Поднят PostgreSQL 16, применена схема `apps/api/db/schema.sql`, запущен `apps/api` (`npm run dev`) с реальным `DATABASE_URL`, и Web запущен без офлайн-режима (смотрит на `http://localhost:3001/api` по умолчанию). Все пункты ниже проверены кликами в управляемом браузере, а не запросами curl напрямую — то есть через тот же путь, каким пользуется живой человек.

### Два реальных бага, найденных и исправленных при этой проверке

Ни один из них не был виден в typecheck/build/тестах — оба всплыли только при попытке пройти публикацию через реальный бэкенд с начала до конца.

1. **Тупик модерации.** Новое объявление создавалось со статусом `moderation`, но в коде не было ни одного места (ни эндпоинта, ни админки, ни джобы), которое переводило бы его в `active`. Публичный список жёстко фильтрует `status = 'active'` — значит, объявление, опубликованное через реальный сервер, было обречено никогда не появиться в каталоге, вопреки прямому требованию ТЗ «опубликованное объявление появляется в общем каталоге». Исправлено: для MVP объявление публикуется сразу активным (`apps/api/src/modules/listings/listings.routes.ts`), как и в автономном (localStorage) режиме. Текст экрана подтверждения на фронтенде был уже готов к обоим вариантам ответа — правки не потребовалось.
2. **Каталог сервера не обновлял экраны.** Объявления с сервера подгружаются асинхронно в общую корзину каталога (`ServerCatalog.ts`) и рассылают событие `nova:server-catalog` — но ни один компонент на него не был подписан. Экран, открытый раньше, чем пришёл ответ API (то есть почти всегда), навсегда остался бы с одними демоданными: реальное объявление лежало бы в базе правильно, но никто бы его не увидел. Добавлен хук `useCatalogVersion()` (`apps/web/src/shared/api/useServerCatalog.ts`), подписанный на это событие; подключён в 7 местах, читающих каталог: `ListPage`, `FiltersPage`, `HomePage`, `SearchPage`, `CategoryHomePage`, `DetailPage`, `ChatPage`, `SystemPage`.

### Реализована отсутствовавшая часть: загрузка фото

Поле `photoKeys` и адрес `/media/<key>` были придуманы в форме ответа API, но ничего в проекте их не заполняло: выбранное на публикации фото уходило в base64 только для автономного режима, а на сервере терялось молча (запрос на публикацию просто не включал фото). Реализовано с нуля:
- `apps/api/src/modules/uploads/uploads.routes.ts` — `POST /api/uploads` (только для вошедших), `multer.diskStorage`, лимит 900 КБ (тот же, что фронтенд обещает в подсказке), проверка MIME-типа (jpeg/png/webp), имя файла — случайный `uuid`, не из пользовательского ввода.
- `apps/api/src/index.ts` — `/media` отдаётся как статика из той же папки, куда пишет `multer`.
- `apps/web/src/shared/api/listings.ts` — `uploadPhoto()`: конвертирует выбранный data URL в файл и грузит его как `multipart/form-data` (не через общий JSON-клиент).
- `apps/web/src/categories/ui/WizardPage.tsx` — перед публикацией на сервере выбранное фото сначала грузится, и в объявление уходит его ключ; если загрузка не удалась, публикация всё равно происходит (без фото), а не рушится.
- Новая зависимость: `multer@2` + `@types/multer` в `apps/api` (нужна для приёма файлов — `express.json()` их не понимает и лимитирован 1 МБ, что не покрыло бы даже 900 КБ фото в виде base64).

## Известные ограничения (честно, без приукрашивания)

1. **SMS реально не отправляется.** Код входа печатается в лог сервера, а не уходит через SMS-провайдера — это единственная часть, которую нельзя закрыть без внешнего аккаунта и его ключей (Twilio, SMS.ru и т.п.), которых у меня нет. Механизм (генерация, хеш с солью, ограничение частоты, срок действия, число попыток) — настоящий и рабочий; не хватает только последнего шага передачи провайдеру.
2. **Модерации в человеческом смысле нет.** Чтобы не оставить тупик (см. выше), объявление публикуется сразу активным, без проверки человеком перед показом другим пользователям. Для реального публичного маркетплейса это осознанный компромисс MVP, а не то, что можно молча оставить: перед открытием для посторонних пользователей понадобится либо очередь модерации с админкой, либо автоматические фильтры (спам, запрещённый контент).
3. **Не задеплоено.** Всё выше проверено локально, в этом контейнере: без HTTPS, без секретов в защищённом хранилище, без мониторинга, без бэкапов базы, без нагрузочного тестирования. Это разработческая проверка «работает от начала до конца», а не готовая продакшн-инфраструктура.
4. **Отдельного аудита безопасности API не проводилось** — за рамками того, что видно по коду (параметризованные запросы, поколоночная валидация `zod`, сравнение кода за постоянное время, ограничение частоты запроса кода, ограничение размера тела запроса).
5. **Mobile не запускался на симуляторе/устройстве** и **не подключён к реальному API объявлений вообще** (только общая логика категорий/данных и переводы из `packages/core` — раздел объявлений там всегда локальный/демо, это не новый пробел, а как было изначально). Эта среда — headless-контейнер без Xcode/Android SDK/эмулятора; проверено только `tsc --noEmit` и статическим анализом.
6. **Не пройдены вручную все 12 категорий по отдельности** — см. таблицу сценариев выше.
7. Vite при сборке предупреждает о размере главного чанка (>500 КБ после минификации) — предупреждение, не ошибка.
8. Переводы (10 языков, ~3000 строк) не проходили вычитку носителем языка.

## Итог

Все автоматические проверки (install/typecheck/test/build, включая Mobile typecheck) — **PASS**. Web полностью проверен вживую как в автономном режиме, так и через настоящий PostgreSQL + API: вход, публикация, фото, видимость в каталоге/поиске/карточке — весь путь целиком, не отдельными кусками. При этой проверке найдены и исправлены два реальных бага (тупик модерации, не обновляющийся каталог) и реализована ранее отсутствовавшая загрузка фото — без них публикация через реальный сервер выглядела бы рабочей в интерфейсе, но объявление никогда не увидел бы никто, кроме автора.

**Это делает проект технически полноценным работающим MVP** — фронт, бэк и база связаны честно, не на словах. Это **не то же самое**, что готовый к публичному коммерческому запуску продукт: SMS не подключён, модерации в человеческом смысле нет (осознанная замена — мгновенная публикация), инфраструктура не развёрнута, аудита безопасности не было. Эти четыре пункта — не забытые технические долги, а решения, которые требуют либо внешних учётных данных (SMS-провайдер), либо решения человека, отвечающего за продукт (политика модерации, инфраструктура, аудит) — не то, что можно закрыть кодом изнутри одной сессии без такого решения.
